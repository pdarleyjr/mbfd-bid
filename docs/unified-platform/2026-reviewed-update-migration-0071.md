# Controlled production migration 0071

This procedure applies only `0071_bid_evidence_reviewed_updates.sql`, after the reviewed release reaches main and its five required checks pass. It does not capture an evidence update, Save a definition, create or repoint a Mock, start a Real bid, or enable Portal writeback. Production deployment continues to use the existing read-only migration guard, which requires the exact canonical ledger through 0071.

The accountable release operator performs the operation in a clean checkout of the verified release SHA. Check the actual `git rev-parse HEAD`; a workflow's `GITHUB_SHA` must not stand in for a different checked-out revision. Record the SHA of the exact SQL file being applied. The production database is `mbfd-bid-production`, ID `df132142-f00a-45a5-b981-68a94861473f`. Confirm this against the checked-out production binding and the remote database identity.

1. Verify Real remains inactive and Portal writeback remains explicitly disabled. Obtain a fresh authorized production backup through the existing manual backup workflow. Download and privately verify both the SQL object and its recovery receipt from the production backup bucket. Match the SQL bytes/hash and size to that receipt, verify its Time Travel bookmark and capture instant, and require its source commit to match the actual release SHA. Retain the verified SQL, recovery object key, receipt SHA and bookmark privately.
2. Read the remote migration ledger and pending migration list immediately before application. The ledger must equal the 70 canonical preceding filenames in order; the pending list must contain exactly `0071_bid_evidence_reviewed_updates.sql`. Stop for any missing, additional, reordered or unexpected migration.
3. Privately capture before-operation table witnesses: stable ordered complete rows, row counts and SHA-256 digests for the existing tables, including the original evidence freeze, all definition versions/heads, every session and frozen policy snapshot (including Peter's existing Mock), canonical state/order/bids/command receipts/events/outbox, approved personnel/qualification/assignment/source-import records, configuration receipts, audit log and Portal queue. Record database integrity `ok` and zero foreign-key violations. Use the same row ordering and hashing for the after witness. Include every existing table being witnessed in both maps; the verifier requires the protected core names and compares all supplied entries.
4. Build the private verifier input using those actual observations, the exact SQL SHA, production identity, release SHA, verified operator subject, operation start instant, recovery receipt object key, exact preledger and pending list. Run `scripts/verify-reviewed-update-migration.mjs` in `before` mode with the actual private input, recovery receipt and downloaded SQL files. This mode verifies evidence and writes a private preflight receipt; it performs no remote operation. It requires the operation boundary to be within five minutes and the verified bookmark within two hours of that boundary.
5. After preflight passes, recheck the remote pending list is still exactly 0071. Explicitly invoke the existing Wrangler D1 migration apply command for `mbfd-bid-production`, `--remote --env production`. Keep its raw output private. This is a separately authorized migration operation; never add migration apply to the deployment workflow.
6. Read the postledger and after witnesses immediately. Require the exact 71 canonical filenames, identical existing table counts and digests, integrity `ok`, zero foreign-key violations, an empty new `bid_evidence_reviewed_updates` table, and the new source revision singleton at zero. Record the actual completion instant. Run the same verifier in `after` mode to produce a new private receipt; it refuses to overwrite an existing receipt file. The receipt binds the database, release, SQL, before/after ledger hashes, preserved table hash, verified backup/recovery hash and bookmark, actor and operation instants.
7. Retain the private receipt and its SHA alongside the existing recovery evidence. Include both actual receipt references in the release's `backup_evidence`. Run the existing read-only production migration guard before deploying the exact checked release. After migration and before source review/capture, verify the original frozen source and Peter's Mock remain unchanged.

The verifier CLI accepts five explicit arguments after its filename: `before` or `after`, private input JSON path, verified recovery JSON path, verified backup SQL path, and a new private output path. Its input contains `environment`, `database`, `databaseId`, `releaseSha`, `migrationSha256`, `actorSubject`, `startedAt`, `recoveryReceiptKey`, `pendingMigrations`, and `before`; `after` mode also requires `appliedAt` and `after`. Each witness contains `migrations`, `integrity`, `foreignKeyViolations`, and `tables` mapping table names to `{count, sha256}`. The after witness additionally contains `reviewedUpdates` and `reviewedUpdateSourceRevision`.

If any witness differs, a receipt is unavailable, or the outcome is uncertain, stop the release. Preserve the private failure evidence and use the existing authorized recovery procedure only after its own guards pass. Do not edit source rows, erase audits or replace frozen evidence to force a matching witness. A successful migration receipt proves this schema operation; it does not prove source review, an update capture, deployment, or browser acceptance.
